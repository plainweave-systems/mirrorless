# One task API, three server languages

These are interchangeable **real HTTP servers**, not browser-side mock stores. Run exactly one, then start any of the browser examples. The examples request `/api` through their development server's proxy to `http://127.0.0.1:4000`.

No framework, database, npm install, or third-party server dependency is required:

```sh
# From the Mirrorless repository root; choose ONE:
node examples/servers/node/server.js
python3 examples/servers/python/server.py
go run examples/servers/go/main.go
```

Each prints its loopback URL. Stop it with Ctrl+C. `PORT=4100` overrides the port; update your browser demo's proxy target accordingly. `PORT=0` selects an unused ephemeral port, which is useful for tests.

## What this demonstrates

The server owns task entities. A browser owns its form draft, selection, pending interactions, and other local state. It receives task lists, selected tasks, and summaries as read inputs, rather than maintaining another task collection that command callbacks must patch.

A command's response is intentionally **not** the corresponding read representation:

```text
POST /api/tasks       -> { "id": "3" }
GET /api/tasks/3      -> { "id": "3", "title": "An example", "done": false }
PATCH /api/tasks/3    -> { "ok": true }
GET /api/summary      -> { "total": 3, "done": 1 }
```

Mirrorless applies the application's declared command→read rules and obtains the representations again. The server does not implement a Mirrorless protocol or know which components are mounted.

## Shared HTTP contract

| Method | Path | Request JSON | Response JSON |
| --- | --- | --- | --- |
| GET | `/api/tasks` | — | Array of tasks |
| GET | `/api/tasks/:id` | — | One task |
| GET | `/api/summary` | — | `{ total, done }` |
| POST | `/api/tasks` | `{ title }` | HTTP 201 `{ id }` |
| PATCH | `/api/tasks/:id` | `{ title?, done? }` | `{ ok: true }` |
| DELETE | `/api/tasks/:id` | — | `{ ok: true }` |

A task is `{ id: string, title: string, done: boolean }`. IDs are generated by the server, starting at `"3"`; a restart restores the same two fixtures:

```json
[
  { "id": "1", "title": "Keep client state local", "done": false },
  { "id": "2", "title": "Let server data flow", "done": true }
]
```

Titles are trimmed and must contain 1–200 Unicode code points. `done` must be a JSON boolean, not a string or number. PATCH requires at least one supported field; POST accepts only `title`. Unknown fields are rejected. Request bodies must be JSON objects with `Content-Type: application/json`, and cannot exceed 16,384 bytes. Both fixed-length and chunked HTTP request bodies are supported.

Errors use a non-2xx HTTP status and `{ error: string }`. Missing tasks and routes return 404; unsupported methods return 405 with `Allow`; invalid input returns 400; unsupported content type returns 415; oversized bodies return 413. Error wording is not an API guarantee. Responses use `Cache-Control: no-store` so demonstrations obtain actual server representations instead of browser HTTP-cache entries.

## Make an external change

With a browser demo open, change data independently of its command handler:

```sh
curl -i -X PATCH http://127.0.0.1:4000/api/tasks/1 \
  -H 'Content-Type: application/json' \
  -d '{"done":true}'
```

If the demo enables `startLiveRefresh`, its timer emits the virtual `RefreshTasks` command, and the affected interested reads fetch the change. Without a timer or another invalidation signal, use the demo's refresh control. Opening two demos makes the same distinction visible: their server data comes from the same process, while their drafts and selections remain independent.

These sample servers intentionally do not implement WebSockets. A real application's socket messages can trigger virtual commands without changing the read/command HTTP API.

## Tests

```sh
node --test tests/examples/server-parity.test.js
```

The suite runs real loopback HTTP requests against all three languages. It checks initial reads, distinct command receipts, create/update/delete, invalid fields and JSON, fixed-length and chunked body limits, concurrent IDs, route/method errors, ephemeral ports, and signal-driven shutdown. Python or Go tests are explicitly skipped when the corresponding executable is absent. Go is compiled into a temporary directory; no binary is added to the repository and no external Go module is needed.

## Deliberate demo limitations

- **Ephemeral:** data lives in the server process and disappears on restart. There is no database or persistence.
- **Single process:** these examples do not coordinate several workers or provide distributed consistency.
- **Local development only:** CLI processes bind to `127.0.0.1`, not a public interface. There is no authentication, authorization, TLS, rate limiting, or production hardening. Do not publish them through a tunnel or deploy them as-is.
- **No permissive CORS:** browser demos use their same-origin Vite proxy. A browser pointed directly at a different API origin needs an intentional CORS policy; these examples do not enable one indiscriminately.
- **No static file serving:** these processes expose only the JSON API. They do not serve project files or read credentials.
- **Bounded requests, not durable transactions:** request-body limits and basic timeouts make local examples safer; they do not turn them into a production backend.
